**Status:** DESIGN ONLY — no runtime implementation  
**Gate:** `MD0_LINKED_DEVICES_ARCHITECTURE`

## 1. Device identity model

### DEVICE_KEY_MODEL

Each linked device holds a **versioned device key bundle** `D_i`:

| Component | Algorithm (v1) | Purpose |
|-----------|----------------|---------|
| `D_sign_priv` / `D_sign_pub` | secp256k1 (Schnorr-capable) | Device event / PoP signatures |
| `D_enc_priv` / `D_enc_pub` | X25519 | Sealed envelopes (history keys, recovery wrap, pairing channel) |
| `deviceId` | UUID v4 (local) | Stable UI / list key (not secret) |
| `scheme` | `sos-device-keys-v1` | Crypto agility |

**Why two pairs:** signing and encryption separation limits blast radius and enables future algorithm swap without rotating both purposes at once. Both are generated **on the device** in platform secure storage.

**Generation location:** exclusively on the device being linked (desktop generates `D_desktop`; new phone generates `D_new`). Never generated by phone for desktop, never by relay.

### DEVICE_PRIVATE_KEY_EXPORTABLE

`conditional`:

- **Android:** prefer Android Keystore with `setIsStrongBoxBacked` when available; `D_*_priv` non-exportable when Keystore-backed. Soft-fallback only if Keystore unavailable → mark device `DEGRADED_SOFT_KEYS` and refuse `RECOVERY_CAPABLE`.
- **Windows desktop:** prefer Windows CNG / TPM-backed key or DPAPI+TPM where available; non-exportable preferred. Soft keys allowed only for `NORMAL_LINKED_DEVICE`, not recovery-capable.
- **Browser-only fallback:** allowed for `NORMAL_LINKED_DEVICE` (IndexedDB + WebCrypto non-extractable when possible). **Forbidden** for `RECOVERY_CAPABLE` (browser cannot safely hold wrapped `K`).

### Storage

| Platform | Location |
|----------|----------|
| `ANDROID_DEVICE_KEY_STORAGE` | Android Keystore aliases `SOS\|device\|sign\|v1\|{deviceId}` and `SOS\|device\|enc\|v1\|{deviceId}`; metadata in app-private encrypted prefs (exclude from backup) |
| `WINDOWS_DEVICE_KEY_STORAGE` | CNG/TPM or DPAPI-sealed file under `%LOCALAPPDATA%\SOS\device\` (backup/cloud sync of private keys **disabled**) |

## 2. Account root vs device keys

```
P  = account root identity (from K)
D_i = linked-device identity (never becomes P)
```

### DEVICE_AUTHORIZATION_MODEL

Canonical object (conceptual JSON, signed as binary canonical form):

```
DeviceAuthorization v1 {
  protocolVersion: "sos-device-auth-v1"
  accountP: hex(P)
  deviceId: string
  D_sign_pub: hex
  D_enc_pub: hex
  capabilities: set { CHAT_SYNC, P2P_CLIENT, CALL_CLIENT, SETTINGS_SYNC,
                      RECOVERY_CAPABLE, ADMIN_DELEGATE? }
  createdAt: unix_ms
  authEpoch: u64          // increments on revoke-all / mass rekey
  expiresAt: unix_ms|null // optional soft expiry; null = until revoked
  label: string           // user-visible device name
  deviceType: PHONE|DESKTOP|TABLET|OTHER
  issuerDeviceId: string  // authorizing device
  nonce: 32B              // unique per auth
}
```

### DEVICE_AUTHORIZATION_SIGNED_BY

**Root account key `K`** (Schnorr signature under `P`).

Only a device that already holds `K` (primary phone, or transient recovery unwrap on recovery-capable desktop during recovery ceremony) may issue/expand authorizations.

Linked devices with only `D_i` **cannot** mint peer authorizations unless capability `ADMIN_DELEGATE` is later defined under AC — out of MD0 scope; default **false**.

## 3. QR pairing ceremony — phone → desktop

### Flow (initial link)

1. **Desktop** generates `D_desktop` (sign+enc), `pairingId`, `E_ephemeral` (X25519), `nonce`, `expiresAt` (e.g. 120s).
2. Desktop displays QR with **public/ephemeral fields only**.
3. **Phone** scans → parses → shows device summary → user confirms strong intent (native confirm / biometric for link).
4. Phone opens encrypted channel to desktop (see §5) using QR transcript.
5. Desktop proves possession of `D_sign_priv` (sign challenge).
6. Phone verifies PoP, binds exact `D_sign_pub`/`D_enc_pub` from QR+PoP transcript.
7. Phone signs `DeviceAuthorization` under `K` with requested capabilities (recovery **opt-in**, not default).
8. Phone sends sealed history-key bootstrap + auth object over channel.
9. Desktop verifies signature under `P`, stores auth, confirms UI “מקושר”.

### QR_FIELDS (v1)

| Field | In QR |
|-------|-------|
| `protocolVersion` | yes (`sos-pair-v1`) |
| `pairingId` | yes |
| `D_sign_pub` | yes |
| `D_enc_pub` | yes |
| `E_ephemeral_pub` | yes |
| `nonce` | yes |
| `expiresAt` | yes |
| `rendezvous` | optional (relay URL / room token — **not** a secret) |
| `sasHint` | optional short code for remote confirm |
| `K` / `nsec` / account material | **NEVER** |

### Required pairing properties

| Flag | Value |
|------|-------|
| `QR_CONTAINS_ROOT_SECRET` | false |
| `QR_PAIRING_BINDS_EXACT_DEVICE_KEY` | true |
| `QR_PAIRING_REPLAY_ACCEPTED` | false |
| `QR_PAIRING_DEVICE_KEY_SUBSTITUTION_ACCEPTED` | false |

**Replay:** `pairingId`+`nonce` single-use; phone records spent IDs; expiry hard-fail.  
**Challenge:** phone → desktop `Sign(D_sign_priv, H("SOS|pair|pop"|transcript))`.

## 4. MITM / device-key substitution

### Attack

QR encodes `D`. Attacker replaces QR or relay payload with `D′` so phone authorizes attacker device.

### PAIRING_MITM_DEFENSE

1. **QR-authenticated transcript:** all channel messages authenticated under keys derived from QR public material (`HKDF(ECDH(E_phone, E_desktop) || transcript)`).
2. **Exact key binding:** phone authorizes only `(D_sign_pub, D_enc_pub)` displayed from scanned QR bytes (hash shown in UI: first/last 4 of `SHA256(D_sign_pub||D_enc_pub)`).
3. **PoP:** desktop must sign with `D_sign` matching QR.
4. **Relay blindness:** relay sees only opaque ciphertext; cannot inject without breaking AEAD.
5. **Optional SAS:** for non-local / high-risk: 6-digit SAS from transcript hash; both sides confirm match before phone signs auth.
6. **User intent:** phone native confirmation names device type + fingerprint.

### PAIRING_TRANSCRIPT_BINDING

```
transcript = H(
  protocolVersion || pairingId || D_sign_pub || D_enc_pub ||
  E_desktop_pub || E_phone_pub || nonce || expiresAt || rendezvous?
)
session_key = HKDF-SHA256(ECDH(...), salt=transcript, info="SOS|pair|v1")
```

AEAD (ChaCha20-Poly1305 or AES-GCM) with AAD = transcript. Any `D→D′` substitution fails MAC or PoP.

## 5. Rendezvous / transport

### PAIRING_RENDEZVOUS_ARCHITECTURE

**Preferred path:** WebRTC DataChannel (P2P), signaled via short-lived encrypted rendezvous messages.

**Order of attempts:**
1. Same-LAN mDNS / local UDP (optional optimization)
2. WebRTC + STUN
3. WebRTC + TURN (media/data relay — encrypted)
4. Temporary WebSocket pairing relay (ciphertext only)

## 9. Delegated device event model

### DELEGATED_DEVICE_EVENT_MODEL

SO-CALL-native envelope (conceptual):

```
DeviceScopedEvent {
  accountP
  deviceId
  authRef: hash(DeviceAuthorization) or authId
  authEpoch
  payloadType
  payloadCiphertext  // optional E2EE body
  createdAt
  sig_D: Schnorr/ECDSA under D_sign
}
```

Verifier (official client):

1. Load `DeviceAuthorization` for `(P, deviceId)` — signature under `P` valid.
2. `capabilities` allow `payloadType`.
3. `authEpoch` not revoked; not expired.
4. `sig_D` verifies under authorized `D_sign_pub`.
5. Replay: `(deviceId, eventId)` dedupe store.

**Compatibility boundary:** standard Nostr relays may store opaque events; **vanilla Nostr clients will not treat `sig_D` as authorship by `P`**. Interop path = phone co-sign of a normal Nostr event, or future NIP-style delegation if adopted.

**Revocation:** publish/sync `DeviceRevocation { deviceId, authEpoch′, signed_by_P }` — see §17.

## 10–12. Recovery capsule

### RECOVERY_CAPSULE_PURPOSE

Allow an **already recovery-capable** linked desktop to restore **the same** `K`/`P` onto a **new phone** after primary phone loss — without daily use of `K` on desktop and without plaintext `nsec` at rest.

### Separated content classes

| Class | Contents | In capsule? |
|-------|----------|-------------|
| **A ROOT IDENTITY** | `Wrap(K → D_enc_recovery)` envelope only | Yes (recovery-capable only) |
| **B VAULT METADATA** | profile labels, device list ciphertext, settings | Yes (encrypted) |
| **C CONVERSATION/SESSION KEYS** | per-chat/session/file key wraps to `D_enc` | Yes (normal + recovery devices) |
| **D HISTORY DATABASE** | messages/events store | **Separate sync DB**, not inside root capsule |
| **E FILE/MEDIA METADATA** | pointers + key ids | Sync channel / sidecar |

### RECOVERY_CAPSULE_RECOMMENDED_CONTENT

```
RecoveryCapsule v1 {
  scheme: "sos-recovery-capsule-v1"
  accountP
  authEpoch
  rootWrap: {  // ONLY if RECOVERY_CAPABLE
    wrapAlg: "X25519-HKDF-ChaCha20Poly1305"
    epk, ct(K), aad=H("SOS|rootwrap|v1"|P|deviceId|authEpoch)
  }
  vaultMetaCt
  conversationKeyIndexCt   // key ids → wrapped keys for this D
  createdAt, capsuleEpoch
}
```

| Flag | Value |
|------|-------|
| `RECOVERY_CAPSULE_CONTAINS_PLAINTEXT_K` | false |
| `RECOVERY_CAPSULE_CONTAINS_PLAINTEXT_NSEC` | false |

### ROOT_K_RECOVERY_WRAP_MODEL

Hybrid envelope: ephemeral X25519 → HKDF → AEAD wrap of `K`, AAD binds `P|deviceId|authEpoch|capsuleEpoch`.  
Stored under OS keystore-locked file. **Unwrap only during recovery ceremony after strong local confirm.**

| Flag | Value |
|------|-------|
| `ROOT_K_UNWRAPPED_DURING_NORMAL_DESKTOP_OPERATION` | **false** |

## 14. Desktop local strong confirmation

Before any root unwrap or new-phone seal:

## 15. New phone recovery ceremony

1. Old phone lost; desktop is `RECOVERY_CAPABLE` + `LINKED`.
2. New phone installs SO-CALL → generates `D_new` → enters “שחזר ממכשיר מקושר”.
3. Desktop “שחזר טלפון חדש” → shows QR (same pairing protocol, purpose=`RECOVERY`).
4. Mutual transcript bind + PoP + optional SAS.
5. Desktop: strong local confirm (§14).
6. Desktop transiently unwraps `K` in memory (never write plaintext to disk).
7. Desktop seals `K` to `D_new_enc` (same wrap model); sends over AEAD channel.
8. New phone imports into `SosSecureIdentityStore` (same-K only); derives `P′`; **abort if `P′ ≠ accountP`**.
9. Phone signs new `DeviceAuthorization` for itself as primary; may rotate `authEpoch` and re-wrap capsules to remaining devices.
10. History/key sync (§22–25); wipe transient `K` from desktop RAM; zeroize.
11. Optionally revoke lost phone’s `deviceId`.

| Flag | Value |
|------|-------|
| `NEW_PHONE_RECOVERY_PRESERVES_ACCOUNT_P` | true |
| `NEW_PHONE_RECOVERY_GENERATES_NEW_ROOT_K` | false |
| `NEW_PHONE_RECOVERY_REQUIRES_TRUSTED_EXISTING_DEVICE` | true |

## 16. F5B6 Model B integration

MD0 supplies the missing primitive:

| Need | MD0 provides |
|------|----------------|
| Authenticated destination key `D` | QR + PoP + transcript-bound `DeviceAuthorization` |
| Anti-substitution | transcript/AEAD/SAS |
| User intent | phone (or recovery desktop) strong confirm |
| Sealed transfer target | wrap to `D_enc` |

F5B6 sealed Worker→signer→Android path can reuse the **same** destination binding: signer packages sealed blob **to `D_enc` of an authorized device** after MD0-style binding (or phone-initiated seal to scanned `D`).

| Flag | Value |
|------|-------|
| `F5B6_CAN_USE_MD0_DEVICE_BINDING` | **true** |
| `F5B6_MODEL_B_BLOCKER_SOLVED_BY_THIS_ARCHITECTURE` | **true** (design-level; implement after MD2–MD3) |

**Do not implement F5B6 in MD0–MD3.** Insertion: after MD3 (auth object) + MD2 (pairing).

## 17. Device revocation

### DEVICE_REVOCATION_MODEL

User opens Settings → Linked Devices → Revoke.

Issuer (device with `K`, or recovery unwrap once) publishes/syncs:

```
DeviceRevocation {
  accountP, deviceId, prevAuthHash, newAuthEpoch, revokedAt, sig_P
}
```

Revoked `D` must fail verification for new ops; clients drop capabilities immediately when revocation observed.

### DEVICE_REVOCATION_PROPAGATION

1. Local device-list update on issuer.
2. Encrypted sync to all linked devices (device-list is security-critical — not last-write-wins; see §23).
3. Optional Nostr opaque broadcast for multi-device discoverability (encrypted to device keys).
4. Offline devices apply on reconnect; until then **fail-closed** for accepting new delegated events from unknown epochs when policy requires freshness for high-risk ops.

| Rotate? | Item |
|---------|------|
| No | Root `K` / `P` |
| Yes | `authEpoch` |
| Yes | Conversation/session/file keys the revoked device held (re-wrap to remaining `D_i`) |
| Yes | Recovery capsule wraps for remaining recovery devices |
| Yes | Pairing spent-id set unaffected |

### POST_REVOCATION_REKEY_MODEL

`DEVICE_REVOKE_ROTATES_ROOT_ACCOUNT_IDENTITY=false`.  
Treat revocation as **forward secrecy for device-held wraps**, not identity rotation. Residual: revoked device may retain **past** plaintext it already decrypted — user warned; full forensic wipe requires OS-level measures.

## 22. History sync model

### HISTORY_SYNC_MODEL

Incremental, resumable, idempotent:

- Per-device **state vector** / cursor per collection (messages, receipts, settings, device-list).
- Event IDs + content hashes; missing-range pull; tombstones for deletes.
- Deduplicate on `(collection, eventId)`.
- Durable offline outbound queue; ack with idempotency keys.
- **No** daily full DB copy.

---

## 23. Sync ownership (authoritative semantics)

| Data | Authority | Conflict rule |
|------|-----------|---------------|
| Messages (send) | Originating device; causal order | Dedupe by eventId; no silent drop of distinct ids |
| Read receipts | Local device max-watermark merge | Lattice merge (OR of read marks) |
| Seen/presence | Ephemeral per device | Last-update per deviceId |
| Drafts | Local-only unless explicit sync | LWW per draftId OK |
| Settings (non-security) | Merge with field clocks | LWW per field |
| Contacts | Merge | Union + tombstones |
| Deleted messages | Tombstone wins | Tombstone ≥ resurrect |
| Block state | Security | **Quorum of root-signed or higher epoch wins; not LWW** |
| Device list / revocation | Root-signed authEpoch | **Highest valid authEpoch under P; ignore forged** |

## 27. Multiple linked devices

### MAX_LINKED_DEVICES_RECOMMENDED

**8** total (e.g. 2 phones + 3 desktops + tablets), soft-cap with owner override later.

Sync topology: **star via primary** or **mesh with bounded fanout** — prefer **primary-phone-assisted + peer pull** to avoid O(N²) full mesh fanout. Each device syncs state vectors with peers ≤ N-1 but payloads deduped; practical cost O(N) per update with relay assist.

## 38. Device state machine

```
UNLINKED
  → PAIRING_PENDING
  → LINKED
  → RECOVERY_CAPABLE   (explicit upgrade)
  → RECOVERY_PENDING   (new-phone ceremony)
  → RECOVERED          (transient; then LINKED as primary)
  → REVOKED
  → EXPIRED            (if expiresAt set)
```

Illegal transitions fail closed (e.g. UNLINKED ↛ RECOVERY_CAPABLE).

| Attack | Defense | Residual |
|--------|---------|----------|
| QR screenshot reuse | Short TTL + single-use pairingId | User photos QR within TTL |
| QR relay MITM | Transcript AEAD + PoP + SAS | SAS skipped by user |
| D→D′ substitution | Bind scanned bytes + PoP | Compromised phone display |
| Stolen phone | OS lock + revoke from desktop | Unlocked phone = full K |
| Stolen desktop | Soft keys no recovery; Hello; revoke+rekey | Unlocked recovery desktop before revoke |
| Desktop malware | No daily K; confirm for recovery | Malware + Hello phishing |
| Phone malware | Same as today for K | Full account |
| Revoked device reuse | authEpoch + revocation sync | Offline stale window |
| Auth replay | nonce + spent store | Clock skew → prefer expire skew budget |
| Capsule theft | At-rest encrypt + OS | Cold extract + broken OS crypto |
| Sync rollback/replay | Monotonic cursors + sigs + tombstones | Partition until heal |
| History injection | Device auth verify | Compromised authorized D |
| Dup / resurrection | eventId dedupe; tombstone wins | Bug in merge |
| Device-list tamper | Root-signed epoch | If K stolen |
| Clock manip | Skew bounds; prefer logical clocks for sync | Extreme skew fails pairing |

## 42. Trust model

| Component | Trust |
|-----------|-------|

| Authorized phone | Holds K; issues auth |
| Device secure storage | Protects D and wraps |
| Desktop OS | Trusted for recovery-capable path |

| Relay/TURN | Untrusted for confidentiality of secrets (ciphertext OK) |

## 44. Owner decisions required

1. **Default recovery capability on link?** Architecture recommends **NO** (explicit opt-in). Confirm.
2. **`MAX_LINKED_DEVICES` hard cap** — recommend **8**. Confirm.
3. **Standard public Nostr-as-P from desktop** — ship with **phone co-sign only** initially, or invest early in delegated-Nostr profile?

## 45. Implementation roadmap

| Phase | Scope |
|-------|-------|
| **MD1** | Device identity keygen + secure storage (Android + desktop stub) |
| **MD2** | QR pairing protocol (QR fields, transcript, PoP, AEAD channel) |
| **MD3** | DeviceAuthorization + capability classes + list UX |
| **MD4** | Initial history/key sync (sealed key index) |
| **MD5** | Continuous sync / reconciliation / offline queues |
| **MD6** | Recovery capsule (wrap K; at-rest; no daily unwrap) |
| **MD7** | New-phone recovery ceremony |
| **MD8** | Revocation + post-revoke rekey |
| **MD9** | Nostr interop (co-sign path + delegated event verify) |
| **MD10** | Adversarial + scale acceptance |

| Insert | When |
|--------|------|
| **F5B6** | After **MD2+MD3** (destination `D` binding exists) — sealed migration to `D_enc` |
| **F6H** | After **F5B6** (or parallel UX stubs); wires native recovery UI to sealed + MD7 paths |
| **F6J** | Parallel (Android F6 dark rollout); independent of MD |
